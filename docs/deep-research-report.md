# Executive Summary  
Game–boosting “VPN” tools like ExitLag and NoPing use custom overlay networks to route only selected game traffic (e.g. PUBG) through optimized paths, rather than tunneling the user’s entire Internet connection. A client program on Windows installs network hooks (via WFP filters or a virtual TAP adapter) that intercept IP packets from the game process and forwards them into a multipath “game accelerator” network.  These services spin up parallel connections through geographically distributed Points-of-Presence (PoPs) and Relay nodes to the game servers.  They split or duplicate game packets across multiple routes (often UDP by default) and use real-time metrics and AI to select the lowest-latency path.  Packets arriving via the overlay network are reassembled and forwarded to the game server, with duplicates discarded by sequence numbers.  This “multipath” routing can dramatically reduce ping and packet loss compared to ISP-default routes.  Notably, the client software operates in user mode (no kernel injection into the game) and only alters Layer-3 routing for tagged game flows.  Key differences include NoPing’s “Multi-Connection AI” with 5 parallel routes and a “Multi-Internet” feature for using multiple local links simultaneously. ExitLag likewise promotes patented multipath technology and AI-based route selection. However, because only game-related traffic is intercepted (typically identified by process, port or selected server), normal PC Internet use is unaffected.  

 *Architecture:* The client creates an overlay tunnel from the user’s PC to the provider’s network of relay servers.  Traffic from the game (e.g. PUBG’s executable) is sent into this tunnel.  For example, Outfox (a similar booster) creates a TAP/TUN adapter and adds routes so that game data goes via their nearest PoP.  In user-mode WFP mode, a packet filter driver intercepts outgoing packets matching the game’s IP/ports and reroutes them.  The overlay packets are typically UDP (with TCP fallback) and may be encrypted or include integrity metadata.  The client selects multiple relay nodes for each game session.  It splits large game packets into MTU-sized payloads and attaches sequence hashes.  Then it sends copies of each packet on 2–5 (or more) parallel routes through distinct relays.  On the far side (the “edge node” near the game server), duplicates are dropped and the original packet reassembled before forwarding to the game server.

## Client Components and Hooks  
The optimization client runs entirely in user space, without modifying the game process or memory.  It typically installs a packet-filter driver (e.g. a WFP callout or the “Windows Packet Filter”) or creates a virtual network adapter.  For example, NoPing’s installer explicitly asks to install a “Windows Packet Filter” driver.  This component watches outgoing traffic: on a packet’s send event it checks if it matches the configured game filter (by executable name, destination IP/port, or user-selected server).  If matched, the client diverts the packet into the accelerator tunnel instead of the normal route.  Some tools (like Outfox) use a TAP/TUN adapter and simply change the Windows routing table so that chosen game IPs go via that adapter.  Others (NoPing) use WFP to catch packets at the IP layer without an extra interface. In either case, only the game’s traffic is routed through the service; general Internet traffic (browsing, other apps) remains on the ISP’s default path.  

## VPN/Tunnel Protocols and Transport  
These “VPNs for gaming” primarily use UDP tunnels (often on ports like 10008, 443, etc.) to minimize latency.  While no official documentation confirms exact protocols, analyses of similar services (e.g. Mudfish) show they send game data over simple UDP connections with optional Forward Error Correction (FEC) or duplicate packets for resilience.  ExitLag’s patent describes “overlay packets” that could use encryption and metadata. Many user guides mention selecting TCP vs UDP “connections” (e.g. users set 2 TCP/2 UDP channels in ExitLag) but this is to trade off reliability vs speed.  In practice, game packets are encapsulated (possibly plain or encrypted) in the overlay transport; the game server sees them as coming from the service’s exit nodes.  (Notably, some users report ExitLag does *not* change the apparent IP to the game, suggesting it may NAT or otherwise preserve the original source address, but details are opaque.)  

## Traffic Classification and Filtering  
To avoid routing all traffic, the clients filter by process, port and destination. In configuration, users select the game title or server, and the client knows the relevant ports/IPs.  For PUBG on PC, this might include Steam’s ports (TCP 27015, UDP 27015-27031, etc.).  The client’s driver/filter examines each outbound packet: if the process matches (e.g. “TslGame.exe” or the Steam executable) *and* the destination matches one of the game servers, the packet is diverted.  Otherwise it goes normally.  Because the service supports thousands of games, it embeds tables of IP ranges or uses DNS/game-integrated lists for known servers. Some packet shapers (like cFosSpeed) explicitly list game booster executables such as “noping.exe” as programs to classify. Thus per-process (or per-port/IP) rules are the norm.  

## Routing and Splitting Logic  
Once a packet is intercepted, the client’s controller splits it into one or more “overlay packets” and dispatches them across multiple routes.  For each baseline packet, the patent shows an edge node may split it into segments under MTU, then send copies of each segment via different relay paths.  All chosen paths lead through the service’s backbone network of relay servers (located in various regions).  Each overlay packet is annotated with sequencing (metadata IDs or hashes) so duplicates can be identified. The provider’s controllers run path-finding algorithms on a graph of relays, weighting paths by current latency, capacity and jitter.  Many such services advertise AI-driven route selection: NoPing’s blog says it measures ping/jitter on 5 parallel routes every 200 ms and uses machine learning to pick the optimal path for the next interval. ExitLag’s own materials claim a “patented redundant connection” system that switches to a fresh route the instant one degrades. In practice, while packets are in flight, relays continuously monitor performance; if one path slows, future packets switch to a better path automatically.  (An alternative approach, used by Outfox, is single-path tunneling: user traffic goes into one chosen PoP tunnel, without dynamic multipath. In contrast, NoPing/ExitLag send duplicates on multiple links to guard against loss.)  

## Encryption and Encapsulation  
The overlays can include encryption or checksums. ExitLag’s patent explicitly describes optionally encrypting the payload. The primary goal is not secrecy (game data isn’t highly sensitive) but integrity and avoiding ISP shaping. Many gamers note that these tools “do not modify packet contents”, implying they leave the game’s data intact (just rewrapped). On-network traffic between client and exit nodes might be obfuscated (e.g. DTLS or proprietary UDP with CRC), but there are no published standards. Some services use TLS on TCP fallback (for traverse networks) and plain UDP otherwise. The client/relay link therefore behaves like a streaming VPN: encrypted enough to prevent ISP inspection but optimized to add minimal overhead.  

## Relay Network and Topology  
ExitLag and NoPing operate global networks of PoPs and relays.  When a game session starts, the client typically connects to the nearest/popular PoP to enter the overlay. From there, game packets are forwarded to a game-region-specific exit point, then onto the actual game server. For example, NoPing has many servers in Europe, Asia and the Americas; Outfox (as documented) will pick a regional PoP (e.g. Sofia) and route to the destination (e.g. Frankfurt) through its optimized core.  The key difference is that multipath optimizers keep several of these relay routes active in parallel.  In effect, the topology is a fully-meshed overlay of relays: the client’s edge node sends each packet copy to N relays (on different backbones/ISPs), which then race to deliver it to the edge near the game server.  The server-edge then merges results, as shown in Fig.1. Because traffic only enters the overlay for that session, large dedicated PoPs and fiber cross-connections allow the services to avoid Internet congestion on critical segments. (Note: adding more relays only helps up to a point – diminishing returns or costs lead to practical limits of ~3–5 parallel paths.)  

## Latency Optimization, Failover and Leak Prevention  
By design, sending each packet on multiple routes means at least one copy will likely arrive on time despite transient congestion. If one relay path spikes in latency or drops, the others still deliver the packet (and the higher-level network simply ignores the delayed duplicates). ExitLag’s “redundant connection” and NoPing’s “Multi-Connection AI” are examples of this tactic. NoPing even goes further with “Multi-Internet”: if the player has e.g. ethernet and 5G links simultaneously, the software sends duplicate game packets across both physical ISPs. This is not failover (switching on failure) but proactive duplication. In a failover scenario, if the primary overlay link disconnects, the other still uplinks the game (so there’s no instant traffic leak to the original ISP). These tools usually implement a kill-switch-like rule so that if the tunnel closes, game traffic stops rather than leaking out normally.  (However, explicit leak-protection features are rarely advertised; users should assume some risk if the tunnel drops mid-game.)  

## Privacy/Security Implications and Limitations  
Because only game traffic is tunneled, the ISP still sees that you’re connecting to the game’s IPs (or to the accelerator servers if an exit node’s IP is used). The content of packets may be hidden from the ISP if encryption is used, but the overlay provider necessarily sees the original and final IPs and packet sizes. From a privacy standpoint, you are trusting the provider with your gaming metadata. On security, NoPing notes that it does *not* inject or scan application memory, so it doesn’t trigger common anti-cheat measures. However, any networking anomaly can flag some games. In fact, some players have reported bans when game publishers began detecting “altered routing” (especially if too frequent path switching looked like a DDoS). In general though, this class of tool is widely used: Outfox (single-tunnel) has a clean record with kernel-mode anti-cheat, and NoPing claims “zero bans” historically.  

Limitations include the obvious fact that if the game server is very close or on the same ISP, multipath may offer little benefit. Also, multi-ISP features require special hardware (e.g. bridging Wi-Fi+Ethernet) and are uncommon for most users. Overhead is minimal (only redundant data, no per-packet handshake like TCP); CPU use is minor on modern systems. Finally, since these are proprietary networks, there is no public audit of how they handle edge cases or potential traffic shaping on their core; we rely on vendor claims and user tests.

## Conclusions and Indicators  
ExitLag, NoPing and similar apps build an overlay routing layer specifically for game traffic. They use lightweight Windows drivers or virtual NICs to capture per-process packets, then send them via multiple optimized paths through their own servers.  Packet captures on a machine running these tools would show game-bound UDP traffic to the service’s IPs (instead of the game’s real IP), often in parallel streams. Each stream will carry sequence metadata; the same packet data may appear multiple times on different routes (one or more paths delivering each).  Notably, you might see odd packet size headers or nonstandard ports (the tunnel port) and constant relaying to relays.  These are telltale signs of per-process routing.  

In sum, these accelerators operate like specialized, multi-path VPNs: selective tunnel of game data, with redundancy and AI-driven path choice, to minimize latency/jitter. The trade-offs involve complexity and trust: you offload your gaming traffic to a third-party network. The payoff (cited in tests and vendor claims) is lower ping and fewer lost packets. Users should be aware that they must configure the correct game or process filter, and understand any game’s policy on third-party networking tools. Despite marketing claims, no method can beat the speed of light – but by harnessing diverse Internet routes and redundant delivery, these tools can statistically avoid bad hops and reduce spikes.
